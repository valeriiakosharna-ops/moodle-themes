# Разработка и добавление вариантов

Каждая задача уже выполняется в изолированной среде. Используйте существующий checkout;
создавать дополнительный worktree для этой работы не требуется.

## Новый вариант

1. Выберите имя компонента, например `theme_brandboost`, и целевую версию Moodle.
2. Разместите плагин в `themes/brandboost/moodle-5.2/brandboost/`.
   Для другой темы используйте её собственное имя вместо `brandboost`.
   Для другой версии Moodle создайте соседний каталог, например `moodle-4.0/`.
3. Настройте `version.php`, зависимости Boost и PHP/API под фактическую версию Moodle.
   Не ограничивайтесь снижением `requires`: проверьте Bootstrap, layouts, renderers и шаблоны.
4. Добавьте вариант в `catalog.json`: имя темы без `theme_`, версия Moodle, версия плагина,
   release/status, source и archive. Все пути задаются относительно корня репозитория.
5. Добавьте проверки в `tests/<тема>/moodle-<версия>/`, скриншоты в `docs/screenshots/`.
6. Выполните сборку, проверки и `npm run package`. Добавьте ZIP и `SHA256SUMS` в тот же MR,
   что и исходники. Обновите таблицу скачиваний и кнопку в корневом README.

Варианты одной темы используют один компонент, например `theme_brandboost`.
На один сайт устанавливается подходящий вариант; одновременно два варианта одного компонента
не устанавливаются. Версия плагина не должна уменьшаться при обновлении сайта и переходе между вариантами.
Исторические выпуски доступны в Git; при необходимости неизменяемые релизы можно публиковать отдельно.

## Общие команды

```sh
npm ci
npm run build
npm test
npm run package
```

Готовые AMD-модули включаются в Git и ZIP. Сборка ищет JS-файлы в `amd/src` каждого варианта
и записывает именованные AMD-модули в `amd/build`.
Упаковка сохраняет только папку плагина, проверяет компонент/версию по каталогу,
фиксирует время и права файлов. ZIP без дополнительного сжатия выбран для одинаковых байтов
на разных версиях zlib; архив темы небольшой и устанавливается обычным способом.

## Проверки на Moodle 5.2

Используйте отдельный установленный тестовый Moodle 5.2 с PostgreSQL и PHP, поддерживаемым этой версией.
Скопируйте или подключите `themes/brandboost/moodle-5.2/brandboost` в `<moodle>/public/theme/brandboost`.
Права на чтение нужны и CLI, и web-серверу. Завершите установку плагина и выберите Brand Boost.

Из корня Moodle:

```sh
php admin/cli/upgrade.php --non-interactive
php admin/cli/purge_caches.php
php admin/cli/build_theme_css.php --themes=brandboost
```

Серверные проверки используют установленный Moodle и временно создают SCSS-пресет,
удаляемый в `finally`; постоянные настройки сайта не изменяются:

```sh
php tests/brandboost/moodle-5.2/server.php /path/to/moodle/config.php
```

Браузерным проверкам нужен тестовый администратор и курс с несколькими разделами,
учебными материалами и хотя бы одним блоком в правой панели.
Проверка сохраняет штатные пользовательские настройки открытых панелей.
Запускайте из корня репозитория тем:

```sh
npx playwright install chromium
MOODLE_URL=http://127.0.0.1:8080 \
MOODLE_USER=admin \
MOODLE_PASSWORD_FILE=/secure/path/to/test-password \
MOODLE_COURSE_ID=3 \
npm run test:browser
```

Пароль считывается из указанного локального файла и не записывается в отчёты.
Можно использовать `MOODLE_PASSWORD` в окружении процесса.
Если Chromium уже установлен, задайте `BROWSER_EXECUTABLE_PATH`;
`BROWSER_ARGS` принимает JSON-массив дополнительных аргументов браузера.
Результаты и скриншоты сохраняются в игнорируемый `test-results/`.

CI не поднимает базу Moodle: браузерные и серверные проверки нужно выполнять при изменении
поведения или адаптации к новой версии. Укажите точную версию Moodle и выполненные проверки в MR.

## Что проверять вручную на конкретном сайте

Логотипы и favicon, фон и собственные пресеты, сторонние плагины, редактор учебных материалов,
SCORM/iframe, роли преподавателя и студента, длинные названия и локализованный интерфейс.
Автоматическая проверка одной демонстрационной страницы не заменяет проверку всего сайта.
